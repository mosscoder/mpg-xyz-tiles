MPG Ranch · Aerial Survey 2026-07-27 QGIS 4.0.1 · plugin v0.3.0

Viewing drone PMTiles directly in QGIS

A walkthrough of the pmtiles_raster plugin: why QGIS can't open our survey tiles on its own, how the plugin fixes that with nothing to run and nothing to convert, and how to get set up in two steps.

TL;DR

QGIS has no reader for raster PMTiles — the format our published drone orthomosaics use. The pmtiles_raster plugin adds one. Install the plugin ZIP once, open mpg_ranch_imagery.qgs, and all sixteen published captures — four drone seasons (2024–2025) plus twelve whole-ranch fixed-wing flights (2011–2024) — stream straight from cloud storage. No tile server, no GeoTIFF downloads, no conversion.

01 · Background

Why the tiles wouldn't open

Each capture is published as a single PMTiles archive on Google Cloud Storage — 8–13 GB of WebP imagery tiles, zoom 8–21, the same files our web viewer reads. PMTiles is a container that can hold either vector tiles or raster (image) tiles. The format doesn't care; the software reading it does.

Desktop GIS implemented only the vector half. As of July 2026:

ReaderVector PMTilesRaster PMTiles
QGIS 4.2 (current) — nativevia GDALno
GDAL ≤ 3.13 (what QGIS bundles)yesno
QGIS plugin repositoryone plugin exists — a converter, not a viewer
GDAL 3.14 (unreleased, ~Nov 2026)yesyes — new raster driver

So native support is coming: once QGIS ships with GDAL 3.14 (realistically the installers of early 2027), these archives will open like any raster. Until then, something has to bridge the gap — and a local tile-server workaround was ruled out because every viewer would have to keep a server running. Hence: a plugin.

02 · Setup

Install in two steps

  1. Install the plugin (one time)

    In QGIS: Plugins → Manage and Install Plugins → Install from ZIP → choose pmtiles_raster_0.3.0.zip. QGIS enables it automatically.

  2. Open the project

    Open mpg_ranch_imagery.qgs. Sixteen layers load, newest on top, named Year Season Platform — from 2025 Fall Drone back to 2011 Fall Fixed-Wing. Toggle layer visibility to compare years and platforms; imagery streams on demand as you pan and zoom.

New capture published? Layer → Add PMTiles Raster Layer… and paste its URL — or add a layer in any project with the archive URL as the source and pmtilesraster as the provider.

If something looks wrong

  • Layers show as unavailable — the plugin isn't installed or enabled. Check Plugins → Manage and Install Plugins → Installed → PMTiles Raster.
  • Layers load but nothing draws — usually no network path to storage.googleapis.com. The archives are public; no sign-in is needed.
  • Slow first draw at a new location — normal: tiles are fetched from the cloud on first view, then cached for the session.

04 · Under the hood

How a 13 GB file draws in two seconds

A PMTiles archive is a header, an index, and millions of small image tiles in one file. The plugin never downloads the archive — it asks the server for exactly the byte ranges it needs, which is the same trick the web viewer uses.

QGIS render engine
asks the layer for pixels covering the current view
↓  block(extent, size)
pmtiles_raster provider
picks the zoom level matching the view scale, computes which tiles cover it
↓  HTTP range requests (index cached after first use)
visible.pmtiles on cloud storage
returns ~30–100 KB WebP tiles, nothing more
↓  decode + mosaic
ARGB32 raster block
handed back to QGIS progressively — imagery appears as ranges land, and preview passes substitute scaled-up cached parent tiles instantly, like the web viewer

Tile lookup uses the format's Hilbert-curve tile IDs and binary search over gzip-compressed directories, so finding any tile among millions costs a handful of small reads. Directories and recently used tiles are cached in memory and shared across the four layers.

05 · Field notes

The bug that almost sank it

Worth recording, because the failure mode is invisible. The first working prototype rendered… nothing. No error, no crash — blank layers.

The full story, for whoever maintains this

QGIS renders in worker threads. Before each redraw it clones the layer's data provider — C++ calls the Python provider's clone() method through the bindings. The clone comes back into C++, but no Python variable references it anymore, so Python's garbage collector frees the wrapper object.

Two failure stages, depending on ownership:

  • Without transferring ownership, the C++ object is destroyed with the wrapper → segfault inside QgsRasterPipe::interfaceRole's dynamic_cast.
  • With sip.transferto(clone, None), the C++ object survives, but once the wrapper is collected, SIP silently stops dispatching virtual calls to Python. dataType() falls back to “unknown”, the raster pipe quietly refuses the renderer's input, and the layer draws blank.

The fix is two lines in provider.py's clone(): transfer C++ ownership and retain the wrapper in a module-level list, pruned with sip.isdeleted(). The provider-metadata object needs the same treatment. Diagnosed with lldb breakpoints on the render pipeline and Python-side tracing of every virtual; the scripts live in dev/.

Files — everything lives in ~/qgis_pmtiles_plugin/: plugin source in pmtiles_raster/, stakeholder package pmtiles_raster_0.3.0.zip, project mpg_ranch_imagery.qgs, maintenance notes in README.md.

Retirement plan — when QGIS ships with GDAL ≥ 3.14, drop the plugin and open the same URLs through the native raster PMTiles driver.
